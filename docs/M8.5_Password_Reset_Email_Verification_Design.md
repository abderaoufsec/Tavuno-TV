# M8.5 Password Reset and Email Verification Design

**Date:** 2026-09-21
**Status:** Design Phase
**Objective:** Design password reset and email verification flows for account security

---

## Password Reset Flow

### User Request
```
User clicks "Forgot Password"
  ↓
Enters email address
  ↓
POST /v1/auth/password-reset/request
  ↓
Backend:
  - Validate email format
  - Check if email exists in database
  - Generate password reset token
  - Store token in Redis with expiration (1 hour)
  - Send email with reset link
  ↓
Return: 200 OK (generic message to prevent enumeration)
```

### Email Link
```
User receives email
  ↓
Clicks reset link: https://tavuno.com/reset-password?token=<token>
  ↓
OwnTV opens reset screen
  ↓
User enters new password
  ↓
POST /v1/auth/password-reset/confirm
  ↓
Backend:
  - Validate token exists in Redis
  - Validate token not expired
  - Validate password strength
  - Update password in database
  - Delete token from Redis
  - Invalidate all existing refresh tokens
  ↓
Return: 200 OK
  ↓
User can sign in with new password
```

### Security Considerations
- Token expiration: 1 hour
- Single-use tokens (deleted after use)
- Invalidate all existing sessions after reset
- Generic success message (email exists/not exists)
- Rate limiting on request endpoint

## Email Verification Flow

### Registration (Optional)
```
User registers
  ↓
Profile created with status='pending_verification'
  ↓
Generate email verification token
  ↓
Store token in Redis with expiration (24 hours)
  ↓
Send email with verification link
  ↓
Return: 201 Created (status: pending_verification)
```

### Verification
```
User receives email
  ↓
Clicks verification link: https://tavuno.com/verify-email?token=<token>
  ↓
OwnTV calls POST /v1/auth/verify-email
  ↓
Backend:
  - Validate token exists in Redis
  - Validate token not expired
  - Update profile status to 'active' (or keep as configured by FREE_LAUNCH)
  - Delete token from Redis
  ↓
Return: 200 OK
  ↓
User can sign in
```

### Skip Verification (Current Behavior)
```
For initial launch, we can skip email verification:
- FREE_LAUNCH=true: auto-activate, no verification needed
- FREE_LAUNCH=false: create inactive, no verification needed

Email verification can be enabled later via configuration.
```

## Token Storage

### Redis Keys
```
Password reset tokens:
- Key: password_reset:{token}
- TTL: 3600 seconds (1 hour)
- Value: {profile_id, email, created_at}

Email verification tokens:
- Key: email_verification:{token}
- TTL: 86400 seconds (24 hours)
- Value: {profile_id, email, created_at}
```

### Token Generation
```
Use secure random token:
- Length: 32 bytes (64 hex chars)
- Generation: secrets.token_urlsafe(32)
- Uniqueness: Not checked (collision unlikely)
```

## API Endpoints

### POST /v1/auth/password-reset/request
Request: { email }
Response: 200 OK (generic message)
Error: 400 Bad Request (invalid email), 429 Too Many Requests (rate limit)

### POST /v1/auth/password-reset/confirm
Request: { token, new_password }
Response: 200 OK
Error: 400 Bad Request (invalid token, expired token, weak password)

### POST /v1/auth/verify-email
Request: { token }
Response: 200 OK
Error: 400 Bad Request (invalid token, expired token)

## Risks

### Email Delivery
- Risk: Emails may be blocked or go to spam
- Mitigation: Use reputable SMTP provider, DKIM/SPF records

### Token Security
- Risk: Tokens could be intercepted
- Mitigation: Short expiration, single-use, HTTPS only

### Rate Limiting
- Risk: Abuse of password reset endpoint
- Mitigation: Rate limiting per email/IP

### Email Enumeration
- Risk: Different timing for existing vs non-existing emails
- Mitigation: Always return generic message, constant timing

   - Decision: No, skip for initial launch, add later

   - Decision: Yes, security best practice

   - Decision: No for initial launch, add later
