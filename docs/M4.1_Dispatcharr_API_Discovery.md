## Authentication and authorization

The running instance supports two authentication methods:

| Method | Request | Lifetime / notes |
| --- | --- | --- |
| API key | `X-API-Key: <key>` or `Authorization: ApiKey <key>` | A key belongs to one Dispatcharr user. Generating another key replaces that user's previous key. |
| JWT | `POST /api/accounts/token/` with `username` and `password`, then `Authorization: Bearer <access>` | The OpenAPI schema specifies a 30-minute access token; refresh at `POST /api/accounts/token/refresh/`. |

Keys are managed at `GET /api/accounts/api-keys/`, `POST /api/accounts/api-keys/generate/`, and `POST /api/accounts/api-keys/revoke/`. The implementation has **one key per user**, not independently scoped API-key objects. API authentication still evaluates the authenticated user's Dispatcharr authorization; normal read endpoints require an active user with at least the Standard User level. Write operations require an Admin-level user.

No `DISPATCHARR_API_KEY` (or equivalent Tavuno integration credential) is configured in this repository or runtime environment. M4 implementation must use a dedicated active Dispatcharr integration user/API key, supplied through a secret mechanism. It must not use an administrator password or embed a JWT/password in source, documentation, or committed configuration.

## Sensitive-data boundary

The live schema exposes connection-oriented fields that Tavuno must not mirror into its product/control database or API responses:

- Stream `url` and `local_file` fields.
- M3U account credentials, server URLs, files, and filters (`GET /api/m3u/accounts/` may expose sensitive account configuration).
- EPG source URLs, usernames, passwords, or local paths (`GET /api/epg/sources/`).

M4 should retrieve only the permitted metadata necessary for catalogue, mapping, and operational status. Source addresses and credentials remain inside Dispatcharr. Sync logs must redact headers, API keys, URLs carrying credentials, and response bodies containing sensitive fields.

## Mapping and sync foundation

No mapping schema or synchronizer has been added in M4.1. The discovered identifiers establish the proposed direction for M4.2:

1. Use Dispatcharr integer `id` as the required remote resource key and persist its resource type alongside it.
2. Retain Dispatcharr `uuid` where present as an additional immutable-looking correlation value; do not replace the integer API key with it.
3. Treat `stream_id` as provider-facing stream metadata, not a replacement for Dispatcharr's stream `id`.
4. Record the API version observed at each sync and stop safely if the probe does not report the expected `0.27.2` contract.
5. Begin with group/category and channel metadata, then streams, EPG catalogue/programmes, and VOD. Each stage must be idempotent, page-aware, and independently logged.

## M4.2 preconditions

Before coding the first connector slice, provide or configure a dedicated Dispatcharr API key for an active, least-privileged integration user that can read the resources above. Store it only in a local secret/environment mechanism (for example an untracked `.env` value), and do not commit it.

Once that key exists, M4.2 can implement a small authenticated client plus version/credential health checks and tests that use mocked Dispatcharr responses. It should not invoke Dispatcharr mutations.
